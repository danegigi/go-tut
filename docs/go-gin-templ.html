Full Stack Go, Gin, and Templ Tutorial

Build a production-minded server-rendered web application with Go, Gin, and Templ, using openlist.ing as the practical example project.

Audience And Goal

This tutorial is for developers who already understand HTTP, HTML, forms, JSON, databases, and application architecture. It teaches how to build a complete server-rendered Go web application with Gin for HTTP routing and middleware, Templ for type-safe HTML components, and a clean internal package structure.

The example product is openlist.ing, a street-sourced real estate listing platform. Visitors browse property sale and lease signs spotted from the street, submit properties, view listing details, and interact with a CMS that manages content and operational pages.

By the end, you should understand how to:

  • structure a Go web application for maintainability.
  • build Gin routers, handlers, middleware, redirects, and form endpoints.
  • render pages with Templ components.
  • pass request context through services and repositories.
  • validate route behavior with `httptest`.
  • configure local development and production builds.
  • prepare the app for database, security, and deployment hardening.

1. What You Are Building

The tutorial uses this application shape:

openlist.ing/

frontend/   Public property listing website
  cms/        Server-rendered administration app
  database/   Central local database package and seed data

The public frontend exposes pages such as:

  • home page with latest listings.
  • listing search and filters.
  • listing detail page.
  • submit-property form.
  • claim and contact flows.
  • static pages such as about, FAQ, terms, and contact.

The CMS exposes pages such as:

  • dashboard.
  • user and role management forms.
  • page/content forms.
  • property listing management forms.
  • SEO, navigation, footer, theme, and audit settings.

This is a classic server-rendered product: the server handles routes, loads data, renders HTML, and returns complete pages or form redirects.

2. Why Go, Gin, And Templ Work Well Together

Think of the stack in three layers:

  • Go is the engine. It compiles your application into a binary, gives you static types, handles concurrency with goroutines, and provides the standard HTTP foundation.
  • Gin is the traffic controller. It matches URLs to handlers, reads route parameters, parses query strings and forms, serves static files, and runs middleware.
  • Templ is the page builder. It lets you write HTML as typed Go components, generate Go code from those components, and render the result directly to the HTTP response.

In openlist.ing, a typical request works like this:

Browser requests GET /listings?q=maple

Gin matches the /listings route

The handler reads q=maple from the query string

The listing service loads and filters listings

The renderer calls a Templ ListingsPage component

Templ writes HTML to the response

The browser receives a complete server-rendered page

Go: The Application Foundation

Go gives the project a small deployment artifact and straightforward runtime behavior. A basic Go HTTP handler can be written with only the standard library: 

http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    _, _ = w.Write([]byte("ok"))
})
log.Fatal(http.ListenAndServe(":5173", nil))

That example is useful for learning, but real applications quickly need routing, middleware, path parameters, form parsing, static assets, and test helpers. That is where Gin earns its place.

Gin: Routing And Request Handling

Gin gives you a clear way to map routes to handler functions:

router := gin.New()
router.Use(gin.Logger(), gin.Recovery())
router.GET("/", homeHandler)
router.GET("/listings", listingsHandler)
router.GET("/listings/:id", listingDetailHandler)
router.POST("/listings", submitListingHandler)

A handler receives `*gin.Context`, which gives access to query strings, path parameters, form fields, headers, status codes, redirects, and response helpers: 

func listingDetailHandler(c *gin.Context) {
    id := c.Param("id")
    if id == "" {
        c.String(http.StatusBadRequest, "missing listing id")
        return
    }
    c.String(http.StatusOK, "listing id: "+id)
}

For openlist.ing, Gin is responsible for routes like `/listings`, `/submit`, `/contact`, and CMS pages such as `/users`, `/seo`, and `/theme`.

Templ: Typed HTML Components

Templ lets you write HTML components that accept Go values. A small component looks like this: 

templ ListingTitle(address string, city string) {
    <article class="listing-summary">
        <h2>{ address }</h2>
        <p>{ city }</p>
    </article>
}

After running `templ generate`, that component becomes Go code. A Gin handler can render it through a small wrapper: 

func render(c *gin.Context, component templ.Component) {
    c.Status(http.StatusOK)
    c.Header("Content-Type", "text/html; charset=utf-8")
    _ = component.Render(c.Request.Context(), c.Writer)
}

The important idea is that the handler does not concatenate HTML strings. It passes typed data into a typed component.

How The Three Pieces Fit In openlist.ing

A simplified openlist.ing listing route combines all three layers:

func (s *Server) listings(c *gin.Context) {
    rows, err := s.service.All(c.Request.Context())
    if handleErr(c, err) {
        return
    }
    visible := s.service.Filter(rows, listings.Filter{
        Query: c.Query("q"),
    })
    s.renderer.Listings(c, rows, visible)
}

The division of work is clean:

  • Gin gives the handler `c.Query("q")` and the response writer.
  • Go services load and filter typed `Listing` values.
  • Templ receives those listings and renders the page.

This combination is especially good for SaaS dashboards, content-managed sites, public listing pages, admin tools, and form-heavy applications where full-page rendering is simpler and more robust than shipping a large client application.

3. Recommended Project Structure

Use a small, explicit structure before reaching for frameworks inside frameworks.

frontend/

cmd/server/main.go
  internal/config/config.go
  internal/httpx/router.go
  internal/httpx/router_test.go
  internal/listings/model.go
  internal/listings/repository.go
  internal/listings/service.go
  internal/web/helpers.go
  internal/web/render.go
  internal/web/views.templ
  internal/web/views_templ.go
  public/
  data/
  go.mod

For an admin app:

cms/

cmd/server/main.go
  internal/config/config.go
  internal/cms/definitions.go
  internal/httpx/router.go
  internal/httpx/router_test.go
  internal/httpx/view_helpers.go
  internal/httpx/views.templ
  internal/httpx/views_templ.go
  public/
  go.mod
The package responsibilities are clear:
  • `cmd/server` wires the application and starts the HTTP server.
  • `internal/config` reads environment variables and default paths.
  • `internal/httpx` translates HTTP requests into application calls.
  • `internal/listings` contains listing business logic.
  • `internal/web` contains public site rendering.
  • `internal/cms` contains CMS page and field definitions.

A good Go web app is not a pile of route callbacks. It is a small composition of packages with clear ownership.

4. Go Module Setup

A frontend module starts with:

mkdir frontend

cd frontend
go mod init openlist.ing/frontend
go get github.com/gin-gonic/gin@v1.10.0
go get github.com/a-h/templ@latest

Install the Templ CLI:

go install github.com/a-h/templ/cmd/templ@latest

A minimal `go.mod` will include Gin and Templ:

module openlist.ing/frontend

go 1.25.0

require (

github.com/a-h/templ v0.3.1020
    github.com/gin-gonic/gin v1.10.0
)

Templ has two parts: the Go module dependency and the CLI. The module is imported by generated code. The CLI turns `.templ` files into Go code.

5. Configuration

Keep configuration in one package. Do not scatter `os.Getenv` calls across handlers. 

package config
import "os"
type Config struct {
    Port         string
    PublicDir    string
    DataPath     string
    SeedDataPath string
    SiteURL      string
    CMSURL       string
}
func Load() Config {
    return Config{
        Port:         env("PORT", "5173"),
        PublicDir:    env("PUBLIC_DIR", "public"),
        DataPath:     env("DATA_PATH", "data/listings.json"),
        SeedDataPath: env("SEED_DATA_PATH", "data/seed-listings.json"),
        SiteURL:      env("SITE_URL", "http://localhost:5173"),
        CMSURL:       env("CMS_URL", "http://localhost:5174"),
    }
}
func env(key, fallback string) string {
    if value := os.Getenv(key); value != "" {
        return value
    }
    return fallback
}

Local `.env.example` files should document expected values:

DATABASE_PROVIDER=sqlite
DATABASE_PATH=../database/data/myapp.sqlite
SITE_URL=http://localhost:5173
CMS_URL=http://localhost:5174

Configuration should describe deploy-time choices. It should not decide business behavior.

6. Application Entrypoint

The entrypoint should wire dependencies and start the server.

package main
import (
    "log"
    "openlist.ing/frontend/internal/config"
    "openlist.ing/frontend/internal/httpx"
    "openlist.ing/frontend/internal/listings"
    "openlist.ing/frontend/internal/web"
)
func main() {
    cfg := config.Load()
    repo := listings.NewFileRepository(cfg.DataPath, cfg.SeedDataPath)
    service := listings.NewService(repo)
    renderer := web.NewTemplRenderer()
    router := httpx.NewRouter(cfg, service, renderer)
    if err := router.Run(":" + cfg.Port); err != nil {
        log.Fatal(err)
    }
}

Notice what is not here:

  • no listing filtering logic.
  • no HTML strings.
  • no form parsing.
  • no SQL or persistence details beyond constructing the repository.

`main` is the assembly point. Keep it boring.

7. Domain Models

Models should be explicit and small.

package listings

type Mode string

type Status string

const (

ModeSale  Mode = "sale"
    ModeLease Mode = "lease"
    StatusCommunityVisible Status = "community_visible"
    StatusNeedsReview      Status = "needs_review"
    StatusVerified         Status = "verified"
    StatusClaimed          Status = "claimed"
    StatusRemoved          Status = "removed"
)
type Listing struct {
    ID              string `json:"id"`
    Address         string `json:"address"`
    City            string `json:"city"`
    Country         string `json:"country"`
    Mode            Mode   `json:"mode"`
    Type            string `json:"type"`
    Price           string `json:"price"`
    Contact         string `json:"contact"`
    Notes           string `json:"notes"`
    Photo           string `json:"photo"`
    Status          Status `json:"status"`
    Featured        bool   `json:"featured"`
    Claimant        string `json:"claimant"`
    OfficialContact string `json:"officialContact"`
    SpottedAt       string `json:"spottedAt"`
    MapX            int    `json:"mapX"`
    MapY            int    `json:"mapY"`
}

Struct tags make JSON shape explicit. Domain constants keep route handlers from passing arbitrary strings everywhere.

8. Repository Layer

A repository hides persistence. The first implementation can be JSON files for local development. A later implementation can use SQL. 

type Repository interface {
    All(ctx context.Context) ([]Listing, error)
    SaveAll(ctx context.Context, rows []Listing) error
    Reset(ctx context.Context) error
}

A file-backed repository is useful for early product development, demos, and route testing. A SQL-backed repository can implement the same interface later.

The handler should not care whether listings came from JSON, SQLite, PostgreSQL, or an API.

9. Service Layer

The service layer owns use cases. It should contain behavior that would otherwise clutter handlers. 

type Service struct {
    repo Repository
}
func NewService(repo Repository) *Service {
    return &Service{repo: repo}
}
func (s *Service) All(ctx context.Context) ([]Listing, error) {
    return s.repo.All(ctx)
}

Filtering belongs here because it is application behavior, not HTTP behavior. 

type Filter struct {
    Query  string
    Market string
    Mode   string
    Status string
}
func (s *Service) Filter(rows []Listing, filter Filter) []Listing {
    out := make([]Listing, 0, len(rows))
    for _, row := range rows {
        if row.Status == StatusRemoved {
            continue
        }
        if !matchesFilter(row, filter) {
            continue
        }
        out = append(out, row)
    }
    return out
}

Handlers should translate query parameters into a `Filter`. The service should decide what that filter means.

10. Gin Router Construction

Use a server struct for dependencies.

type Server struct {
    cfg      config.Config
    service  *listings.Service
    renderer web.Renderer
}
func NewRouter(cfg config.Config, service *listings.Service, renderer web.Renderer) 
*gin.Engine {
    gin.SetMode(gin.ReleaseMode)
    router := gin.New()
    router.Use(gin.Logger(), gin.Recovery())
    server := &Server{cfg: cfg, service: service, renderer: renderer}
    server.mount(router)
    return router
}

This makes the router easy to test because you can inject temporary repositories, fake renderers, or real Templ renderers.

11. Route Mounting

Routes should be readable at a glance.

func (s *Server) mount(router *gin.Engine) {
    router.Static("/assets", filepath.Join(s.cfg.PublicDir, "assets"))
    router.GET("/styles.css", s.staticFile("styles.css", "text/css; charset=utf-8"))
    router.GET("/site.webmanifest", s.staticFile("site.webmanifest", 
"application/manifest+json; charset=utf-8"))
    router.GET("/", s.home)
    router.GET("/listings", s.listings)
    router.GET("/submit", s.submit)
    router.GET("/claim", s.claim)
    router.GET("/admin", s.admin)
    router.GET("/listings/:id", s.listingDetail)
    router.POST("/contact", s.contactPost)
    router.POST("/listings", s.submitListing)
    router.POST("/claims", s.claimPost)
    router.POST("/features", s.featurePost)
    router.POST("/admin/listings/:id/status", s.statusPost)
}

Static assets, GET pages, and POST actions are easy to identify.

12. Handler Design

A good handler does five things:

  1. read HTTP input.
  2. call a service.
  3. handle errors.
  4. render or redirect.
  5. avoid business logic sprawl.

Example listing handler:

func (s *Server) listings(c *gin.Context) {
    rows, err := s.service.All(c.Request.Context())
    if handleErr(c, err) {
        return
    }
    visible := s.service.Filter(rows, listings.Filter{
        Query:  c.Query("q"),
        Market: c.DefaultQuery("market", "all"),
        Mode:   c.DefaultQuery("mode", "all"),
        Status: c.DefaultQuery("status", "all"),
    })
    s.renderer.Listings(c, rows, visible)
}

Example form handler:

func (s *Server) contactPost(c *gin.Context) {
    if strings.TrimSpace(c.PostForm("name")) == "" ||
        strings.TrimSpace(c.PostForm("email")) == "" ||
        strings.TrimSpace(c.PostForm("message")) == "" {
        c.String(http.StatusBadRequest, "Name, email, and message are required.")
        return
    }
    c.Redirect(http.StatusSeeOther, "/?contact=sent#contact")
}

For browser forms, `303 See Other` is often the right redirect after successful POST. It prevents accidental resubmission when the user refreshes.

13. Error Mapping

Centralize repeated error-to-HTTP behavior.

func handleErr(c *gin.Context, err error) bool {
    if err == nil {
        return false
    }
    if errors.Is(err, listings.ErrNotFound) {
        c.Status(http.StatusNotFound)
        return true
    }
    if errors.Is(err, listings.ErrUnsupportedStatus) {
        c.String(http.StatusBadRequest, "Unsupported status")
        return true
    }
    c.String(http.StatusInternalServerError, err.Error())
    return true
}

This gives domain packages freedom to return domain errors while the HTTP package decides how those errors appear to browsers.

14. Templ Features And How To Use Them

Templ is more than a way to write HTML in Go. It is a component system for server-rendered applications. You write `.templ` files, run `templ generate`, and Templ creates normal Go code that can be compiled, tested, and rendered from handlers.

The main features you will use in openlist.ing are:

  • typed component parameters.
  • component composition.
  • children and layout slots.
  • Go expressions inside markup.
  • loops and conditionals.
  • dynamic attributes.
  • safe URLs for links.
  • helper functions from normal Go files.
  • generated Go render functions.

Component Parameters

A Templ component accepts typed Go parameters. This is the first major benefit over unstructured HTML strings. 

templ ListingTitle(address string, city string) {
    <div class="listing-title">
        <h2>{ address }</h2>
        <p>{ city }</p>
    </div>
}

You call it with normal values:

@ListingTitle(row.Address, row.City)

For openlist.ing, most useful components accept domain types:

templ ListingCard(row listings.Listing) {
    <article class="listing-card">
        <h3>{ row.Address }</h3>
        <p>{ row.City }, { row.Country }</p>
    </article>
}

This makes the component contract obvious. `ListingCard` needs a `listings.Listing`, not a map, JSON blob, or loose set of strings.

Layout Components And Children

A layout component can receive child content with `{ children... }`. 

templ PageShell(title string) {
    <!doctype html>
    <html lang="en">
        <head>
            <meta charset="utf-8"/>
            <meta name="viewport" content="width=device-width, initial-scale=1"/>
            <title>{ title }</title>
            <link rel="stylesheet" href="/styles.css"/>
        </head>
        <body>
            { children... }
        </body>
    </html>
}

A page component wraps its content inside the shell:

templ HomePage(rows []listings.Listing) {
    @PageShell("openlist.ing") {
        @Topbar()
        <main>
            @Hero()
            @LatestProperties(rows)
        </main>
    }
}

Use this pattern for page-level consistency. The shell owns document structure, shared CSS, metadata, scripts, header/footer placement, and global layout. Individual pages own their content.

Component Composition

Templ components should be small enough to name clearly. Instead of one giant home page component, compose it from sections: 

templ HomePage(rows []listings.Listing) {
    @PageShell("openlist.ing") {
        @Topbar()
        <main>
            @Hero()
            @LatestProperties(rows)
            @Testimonials()
            @ContactSection()
        </main>
    }
}

Composition keeps templates readable. It also makes each section easier to change without touching unrelated markup.

Go Expressions In Markup

Use `{ ... }` to insert escaped dynamic text.

<h1>{ row.Address }</h1>

<p class="listing-price">{ row.Price }</p>

<p>{ row.Notes }</p>

Templ escapes text output by default. That is what you want for user-controlled fields such as listing notes, addresses, and contact details.

Use helpers when formatting gets repetitive:

func statusLabel(status listings.Status) string {
    return strings.ReplaceAll(string(status), "_", " ")
}

Then call the helper from the template:

<span>{ statusLabel(row.Status) }</span>

Loops

Use normal Go `for` loops inside components.

templ LatestProperties(rows []listings.Listing) {
    <section class="latest-properties">
        <div class="latest-grid">
            for _, row := range topListings(rows, 8) {
                @ListingCard(row)
            }
        </div>
    </section>
}

This is useful for listing grids, CMS sidebar navigation, dropdown options, breadcrumbs, and repeated cards.

For select fields, the pattern is the same:

templ PropertyTypeSelect(types []string) {
    <select name="type">
        for _, item := range types {
            <option value={ item }>{ item }</option>
        }
    </select>
}

Conditionals

Use `if` for conditional HTML.

templ StatusBadges(row listings.Listing) {
    if row.Featured {
        <span class="status-pill warning">featured</span>
    }
    <span class={ "status-pill " + string(row.Status) }>{ statusLabel(row.Status) }</span>
}

The CMS uses conditionals for saved notices:

templ CMSPage(page cms.Page, saved bool) {
    @Shell(page.Title) {
        if saved {
            <p class="notice">Saved draft changes for { page.Title }.</p>
        }
        <form method="post" action={ templ.URL("/" + page.Slug) }>
            for _, field := range pageFields(page) {
                @FieldControl(field)
            }
        </form>
    }
}

Use conditionals to include or omit real elements. Do not render hidden placeholder markup unless the client-side behavior needs it.

Switch Statements

Templ supports Go control flow such as `switch`. This is useful for CMS field rendering. 

templ FieldControl(field cms.Field) {
    switch field.Type {
        case "textarea":
            @TextareaField(field)
        case "select":
            @SelectField(field)
        case "checkbox":
            <label><input type="checkbox" name={ field.Name } value="1"/> <span>{ 
field.Label }</span></label>
        default:
            @InputField(field)
    }
}

This keeps the CMS extensible. Adding a new field type becomes a focused component change.

Dynamic Attributes

Use `{ ... }` inside attributes when the value changes per record.

<img class="listing-photo-img" src={ listingImageURL(row) } alt=""/>

<button aria-label={ "Save " + row.Address }>♡</button>

<span class={ "status-pill " + string(row.Status) }>{ statusLabel(row.Status) }</span>

Dynamic attributes are ideal for classes, form values, ARIA labels, image sources, IDs, and data attributes. 

For links built from dynamic values, use `templ.URL`:
go
<a href={ templ.URL("/listings/" + row.ID) }>View details</a>

That makes intent clear: this expression is meant to be used as a URL.

Forms And Required Fields

Templ works well for HTML forms because forms are mostly structured HTML with a few dynamic values. 

templ InputField(field cms.Field) {
    if field.Required {
        <label><span>{ field.Label }</span><input type={ inputType(field) } name={ 
field.Name } placeholder={ field.Placeholder } required/></label>
    } else {
        <label><span>{ field.Label }</span><input type={ inputType(field) } name={ 
field.Name } placeholder={ field.Placeholder }/></label>
    }
}

In Go templates, boolean attributes such as `required` are easiest to handle with separate branches. This keeps generated HTML explicit and easy to inspect.

Helper Functions

Keep helper functions in normal `.go` files in the same package as your `.templ` files. 

package web
func listingImageURL(row listings.Listing) string {
    if row.Photo != "" {
        return row.Photo
    }
    return defaultImageForType(row.Type)
}

Then use the helper in the template:

<img src={ listingImageURL(row) } alt=""/>

Good helper candidates include:

  • status labels.
  • image fallback URLs.
  • date formatting.
  • short text summaries.
  • class-name builders.
  • filtered slices such as latest or featured listings.

Avoid putting business decisions in helpers. If a rule changes application behavior, it belongs in a service, not a view helper.

Safe HTML And User Content

By default, Templ escapes text inserted with `{ value }`. Keep that default for user content.

Use safe HTML mechanisms only for trusted content that you control and sanitize before rendering. A CMS rich-text field should not become raw HTML until you have a sanitization strategy.

For openlist.ing, listing notes, addresses, contact fields, and user-submitted descriptions should render as escaped text.

Datastar, HTMX, And Custom Attributes

Templ can preserve custom HTML attributes used by lightweight frontend libraries. For example, the frontend can keep Datastar attributes in normal markup:

<body data-signals="{ selectedListing: '', selectedStatus: 'all' }">

{ children... }

</body>

Dynamic data attributes also work:

<article data-show={ filterExpression(row) }>

@ListingCardBody(row)

</article>

This makes Templ a good fit for hypermedia-style applications: server-rendered HTML first, light declarative interactivity where needed.

Generated Code Workflow

Templ files are source files, but Go builds the generated files. The workflow is: 

templ generate
go test ./...
go run ./cmd/server

If generation succeeds but Go tests fail, the problem is in the generated Go integration, imports, helper functions, or handler code. If generation fails, the issue is in `.templ` syntax or unsupported template expressions.

Practical Templ Rules For This Project

Use these rules when extending openlist.ing:

  • Create page components for full pages: `HomePage`, `ListingsPage`, `SubmitPage`, `CMSPage`.
  • Create section components for repeated page regions: `Topbar`, `Footer`, `LatestProperties`, `ContactSection`.
  • Create item components for repeated records: `ListingCard`, `Testimonial`, `FieldControl`.
  • Keep business rules in services and formatting helpers in the view package.
  • Use `templ.URL` for dynamic links.
  • Prefer escaped text output for anything users can edit.
  • Run `templ generate` after every `.templ` edit.
  • Run route tests after template changes because templates are part of the HTTP response contract.

Templ is most effective when you treat it as typed HTML composition, not as a place to hide application logic.

15. Rendering Templ From Gin

Create a renderer interface for the pages your router needs.

type Renderer interface {
    Home(*gin.Context, []listings.Listing)
    Listings(*gin.Context, []listings.Listing, []listings.Listing)
    Simple(*gin.Context, string, string)
    Submit(*gin.Context)
    ListingDetail(*gin.Context, listings.Listing)
}

Implement it with Templ:

type TemplRenderer struct{}
func NewTemplRenderer() *TemplRenderer { return &TemplRenderer{} }
func (r *TemplRenderer) Listings(c *gin.Context, all []listings.Listing, visible 
[]listings.Listing) {
    r.render(c, ListingsPage(all, visible))
}
func (r *TemplRenderer) render(c *gin.Context, component templ.Component) {
    c.Status(http.StatusOK)
    c.Header("Content-Type", "text/html; charset=utf-8")
    if err := component.Render(c.Request.Context(), c.Writer); err != nil {
        c.Error(err)
    }
}

This keeps templates out of handlers while still making render calls explicit.

20. Middleware

Gin middleware wraps requests. Start with logging and recovery:

router := gin.New()
router.Use(gin.Logger(), gin.Recovery())

Add middleware for cross-cutting concerns:

func SecurityHeaders() gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Header("X-Content-Type-Options", "nosniff")
        c.Header("X-Frame-Options", "DENY")
        c.Header("Referrer-Policy", "strict-origin-when-cross-origin")
        c.Next()
    }
}

For CMS routes, middleware should eventually enforce sessions, CSRF protection, and permissions. 

cmsGroup := router.Group("/")

cmsGroup.Use(RequireSession(), RequireCSRF())

Middleware should be boring and focused. It should not hide route-specific business rules.

21. Testing Routes

Use `httptest` to verify status codes, redirects, and response bodies. 

func TestFrontendRouteParity(t *testing.T) {
    router := NewRouter(cfg, service, web.NewTemplRenderer())
    assertStatus(t, router, http.MethodGet, "/", "", http.StatusOK)
    assertStatus(t, router, http.MethodGet, "/listings?q=maple", "", http.StatusOK)
    assertStatus(t, router, http.MethodGet, "/listings/missing", "", http.StatusNotFound)
    assertStatus(t, router, http.MethodPost, "/contact", "name=&email=&message=", 
http.StatusBadRequest)
}

Helper:

func assertStatus(t *testing.T, router http.Handler, method, target, body string, want int)

*httptest.ResponseRecorder {

t.Helper()
    req := httptest.NewRequest(method, target, strings.NewReader(body))
    if body != "" {
        req.Header.Set("Content-Type", "application/x-www-form-urlencoded")
    }
    res := httptest.NewRecorder()
    router.ServeHTTP(res, req)
    if res.Code != want {
        t.Fatalf("%s %s status = %d, want %d", method, target, res.Code, want)
    }
    return res
}

Tests should lock down behavior before refactors. That is especially important in server-rendered apps where redirects and form status codes are part of the user experience.

27. Common Mistakes

Avoid these early mistakes:

  • putting all logic in `main.go`.
  • letting handlers become business services.
  • building HTML with string concatenation.
  • skipping `templ generate` before tests.
  • ignoring `context.Context` in repository methods.
  • using `302` for every form redirect instead of intentional `303` behavior.
  • opening database connections per request.
  • hiding dependencies in global variables.
  • skipping route tests because pages render in a browser.

The stack rewards explicitness. Keep the boring boundaries intact.

28. Suggested Learning Path

Work through the stack in this order:

  1. Create a Gin router with one static page.
  2. Add a Templ layout and render it from Gin.
  3. Add a typed model and a service method.
  4. Add a listing page with a looped Templ component.
  5. Add a form page and a POST handler.
  6. Add redirects and validation errors.
  7. Add `httptest` route tests.
  8. Add middleware.
  9. Add persistence behind a repository interface.
  10. Add production configuration and build scripts.

This order keeps each concept small enough to understand while still moving toward a real application.

29. Final Architecture Summary

A solid Go, Gin, and Templ application has clear boundaries:

  • Gin owns HTTP.
  • handlers translate requests and responses.
  • services own use cases.
  • repositories own persistence.
  • Templ owns HTML.
  • config owns environment.
  • tests own behavior verification.
  • `cmd/server` owns assembly.

openlist.ing follows that shape. The result is a server-rendered application that is easy to run locally, easy to test, easy to compile, and ready for production hardening.

DevOps: Deploying a Go + Gin + templ App

A Go web app compiles to a single static binary, which makes it one of the easiest things to containerize and deploy. This section walks up the ladder: a single Docker image, then Docker Compose for local multi-service dev, then Docker Swarm for a small cluster, and finally Traefik as a reverse proxy that gives you automatic HTTPS and routing. Each step builds on the previous one.

1. Dockerfile — a multi-stage build

The goal of a Go Dockerfile is a tiny final image that contains only the compiled binary and static assets — no Go toolchain, no source. A multi-stage build does this: a "builder" stage compiles, and a minimal final stage copies just the binary out. 

# ---- Stage 1: build ----
FROM golang:1.26-alpine AS builder
WORKDIR /src

# Install the templ + tailwind toolchain if you generate at build time.
# (Alternatively, commit the generated *_templ.go and app.css and skip this.)
RUN go install github.com/a-h/templ/cmd/templ@latest

# Cache dependencies first: this layer only rebuilds when go.mod/go.sum change.
COPY go.mod go.sum ./
RUN go mod download

# Now copy the source and build.
COPY . .
RUN templ generate ./...
# CGO_ENABLED=0 makes a fully static binary (no libc), so it runs on scratch/alpine.
# -ldflags "-s -w" strips debug info to shrink the binary.
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server ./cmd/server

# ---- Stage 2: run ----
FROM alpine:3.20
# ca-certificates lets the app make HTTPS calls (Stripe, S3, etc.).
RUN apk add --no-cache ca-certificates
WORKDIR /app

# Copy only what the runtime needs: the binary and static assets.
COPY --from=builder /app/server /app/server
COPY --from=builder /src/static /app/static

# Run as a non-root user for safety.
RUN adduser -D -u 10001 appuser
USER appuser

EXPOSE 8080
ENTRYPOINT ["/app/server"]

What it does: stage 1 pulls the full Go image, generates templ code, and compiles a static binary. Stage 2 starts from a ~5 MB Alpine base and copies in only the binary and static/ directory. The final image is typically 15–25 MB instead of the ~800 MB of the builder. CGO_ENABLED=0 is the key flag — it produces a self-contained binary with no dynamic library dependencies, so it can even run FROM scratch.

Build and run it:

docker build -t myapp:latest .
docker run --rm -p 8080:8080 --env-file .env myapp:latest

2. Docker Compose — app + database together

A real app needs a database. Docker Compose describes multiple services in one compose.yaml and wires them onto a shared network so they can find each other by name. This is the standard local-dev and small-single-host setup. 

services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      # Compose lets services reach each other by SERVICE NAME as the host.
      DATABASE_URL: "user:password@tcp(db:3306)/myapp?parseTime=true"
      JWT_KEY: "${JWT_KEY}"          # read from your shell / an .env file
      SESSION_SECRET: "${SESSION_SECRET}"
      PORT: "8080"
    depends_on:
      db:
        condition: service_healthy   # wait until the DB is actually ready
    restart: unless-stopped

  db:
    image: mysql:8.0
    environment:
      MYSQL_DATABASE: myapp
      MYSQL_USER: user
      MYSQL_PASSWORD: password
      MYSQL_ROOT_PASSWORD: rootpassword
    volumes:
      - dbdata:/var/lib/mysql        # persist data across container restarts
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  dbdata:

What it does: two services — app and db — on an automatically-created private network. The app reaches MySQL at host db (the service name) rather than an IP, because Compose provides internal DNS. depends_on with condition: service_healthy makes the app wait for the DB's healthcheck to pass before starting, avoiding "connection refused" on boot. The named volume dbdata keeps the database on disk so data survives docker compose down and restarts. 

# Bring the whole stack up (build if needed), in the background.
docker compose up -d --build

# Tail logs, then tear it down (keeping the volume).
docker compose logs -f app
docker compose down

3. Docker Swarm — scaling to a cluster

Compose runs on one host. Docker Swarm turns a set of machines into a single cluster and schedules replicas across them, with built-in load balancing and rolling updates — using nearly the same YAML. It's the lightest-weight orchestrator (Kubernetes is the heavier alternative). 

# Initialize a swarm on the manager node.
docker swarm init

# The same compose file works, but now under the `deploy:` key.
# Deploy it as a "stack":
docker stack deploy -c compose.yaml myapp

Add a deploy block to the app service to control replicas and rolling updates: 

services:
  app:
    image: myregistry/myapp:latest   # Swarm pulls from a registry, not `build:`
    deploy:
      replicas: 3                      # run 3 copies, load-balanced
      update_config:
        parallelism: 1                 # update one replica at a time
        delay: 10s                     # wait between each (zero-downtime rollout)
        order: start-first             # start the new one before stopping the old
      restart_policy:
        condition: on-failure
      resources:
        limits:
          cpus: "0.50"
          memory: 256M
    ports:
      - "8080:8080"

What it does: Swarm runs 3 replicas of the app and spreads incoming requests across them via its built-in routing mesh — hitting any node's port 8080 reaches a healthy replica. update_config defines a rolling update: when you push a new image and re-run docker stack deploy, Swarm replaces replicas one at a time (start-first brings the new container up before killing the old), so the service stays available throughout. Note the switch from build: to image: — Swarm pulls a pre-built image from a registry, so your CI builds and pushes the image, and the stack file just references it.

4. Traefik — reverse proxy + automatic HTTPS

You don't want to expose the app on port 8080 to the world, hand-manage TLS certificates, or reconfigure a proxy every time you scale. Traefik is a reverse proxy that discovers your containers automatically (via Docker labels), routes by hostname/path, and provisions Let's Encrypt certificates for you. 

services:
  traefik:
    image: traefik:v3.1
    command:
      # Watch Docker for containers to route to.
      - "--providers.docker=true"
      - "--providers.docker.exposedbydefault=false"  # only route labeled containers
      # Entry points: 80 for HTTP (redirected), 443 for HTTPS.
      - "--entrypoints.web.address=:80"
      - "--entrypoints.websecure.address=:443"
      # Automatic TLS via Let's Encrypt (ACME).
      - "--certificatesresolvers.le.acme.tlschallenge=true"
      - "--certificatesresolvers.le.acme.email=you@example.com"
      - "--certificatesresolvers.le.acme.storage=/letsencrypt/acme.json"
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - "/var/run/docker.sock:/var/run/docker.sock:ro"  # read Docker events
      - "letsencrypt:/letsencrypt"                       # persist certificates

  app:
    build: .
    environment:
      PORT: "8080"
    labels:
      - "traefik.enable=true"
      # Route requests for this hostname to this service.
      - "traefik.http.routers.app.rule=Host(`app.example.com`)"
      - "traefik.http.routers.app.entrypoints=websecure"
      - "traefik.http.routers.app.tls.certresolver=le"
      # Tell Traefik which internal port the app listens on.
      - "traefik.http.services.app.loadbalancer.server.port=8080"

volumes:
  letsencrypt:

What it does: Traefik mounts the Docker socket (read-only) to watch containers as they start and stop. Because the app carries traefik.enable=true and a Host(...) rule label, Traefik automatically creates a route: HTTPS requests for app.example.com are forwarded to the app's internal port 8080. The certresolver=le label triggers Traefik to obtain and renew a Let's Encrypt certificate for that hostname over the TLS challenge — no manual certbot. The app itself keeps serving plain HTTP on 8080 inside the network; Traefik terminates TLS at the edge. When you scale the app to multiple replicas (in Swarm), Traefik load-balances across them automatically because it discovers each one by its labels.

Putting it together

Tool Solves Use when
Dockerfile Reproducible, tiny runtime image Always — the foundation for everything below
Docker Compose App + DB + friends on one host Local dev, and small single-server deployments
Docker Swarm Replicas across a cluster, rolling updates You've outgrown one host but don't want Kubernetes
Traefik Reverse proxy, routing, automatic HTTPS You need TLS and clean hostnames in front of it all

A common production shape for a small team: CI builds the multi-stage image and pushes it to a registry; a Swarm stack file references that image with replicas and a rolling update_config; and Traefik sits in front terminating TLS and routing by hostname. You get zero-downtime deploys, automatic certificates, and horizontal scaling with a handful of YAML files and no Kubernetes.

Kubernetes: From Pods to a Real Deployment

Docker Swarm is the easy on-ramp, but most companies run Kubernetes (often written "K8s" — K, then 8 letters, then s) in production. Kubernetes is a container orchestrator: you tell it the desired state ("I want 3 copies of this app running, reachable at this address"), and it continuously works to make reality match — restarting crashed containers, rescheduling them when a machine dies, and rolling out new versions without downtime. This section builds up from the smallest unit to a full deployment, assuming you've never touched K8s before.

The mental model: desired state and the control loop

Everything in Kubernetes is an object you describe in YAML and submit to the cluster. The cluster's "control plane" runs controllers that constantly compare desired state (what your YAML says) against actual state (what's running) and act to close the gap. You almost never start containers by hand — you declare what you want and let Kubernetes maintain it. If you delete a running app container, Kubernetes notices it's one short of the desired count and starts a new one within seconds. That self-healing loop is the whole point.

1. Pods — the smallest deployable unit

A Pod is one or more containers that share a network address and storage, scheduled together on the same machine (node). For a typical web app, a Pod holds a single container: your Go binary. You rarely create Pods directly (a bare Pod isn't restarted if it dies), but understanding them is the foundation. 

# pod.yaml — the simplest possible object (for learning; not for production)
apiVersion: v1
kind: Pod
metadata:
  name: myapp
  labels:
    app: myapp            # labels are key/value tags used to select objects later
spec:
  containers:
    - name: server
      image: myregistry/myapp:latest
      ports:
        - containerPort: 8080

# Apply it, then inspect.
kubectl apply -f pod.yaml
kubectl get pods                     # STATUS should become Running
kubectl logs myapp                   # view the container's stdout
kubectl describe pod myapp           # events + why it's pending/crashing
kubectl delete pod myapp             # gone for good — nothing restarts it

What this shows: kubectl is the CLI that talks to the cluster. apply -f submits an object; Kubernetes schedules the Pod onto a node and pulls the image. The labels (app: myapp) are just tags — but they're how everything else finds this Pod later. The lesson: a bare Pod has no supervision, so we never ship them alone. That's what a Deployment is for.

2. Deployments — self-healing, scaling, and rolling updates

A Deployment is the object you actually use. It manages a set of identical Pods for you: it keeps a target number running (self-healing), lets you scale that number up or down, and rolls out new image versions one Pod at a time with zero downtime. 

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3                       # desired number of Pods
  selector:
    matchLabels:
      app: myapp                    # this Deployment manages Pods with this label
  template:                         # the Pod "cookie cutter" — how each replica looks
    metadata:
      labels:
        app: myapp                  # must match the selector above
    spec:
      containers:
        - name: server
          image: myregistry/myapp:1.0.0   # pin a real version, never :latest in prod
          ports:
            - containerPort: 8080
          env:
            - name: PORT
              value: "8080"
          resources:
            requests:               # what the scheduler reserves for this Pod
              cpu: "100m"           # 100 millicores = 0.1 CPU
              memory: "64Mi"
            limits:                 # hard ceiling; exceeding memory = OOM-killed
              cpu: "500m"
              memory: "256Mi"
          # Health probes let Kubernetes know if the container is alive & ready.
          livenessProbe:            # if this fails, K8s RESTARTS the container
            httpGet: { path: /healthcheck, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 10
          readinessProbe:           # if this fails, K8s stops sending it traffic
            httpGet: { path: /healthcheck, port: 8080 }
            initialDelaySeconds: 3
            periodSeconds: 5

kubectl apply -f deployment.yaml
kubectl get deployments            # READY should read 3/3
kubectl get pods                   # 3 Pods, names like myapp-7d9f8c-abcde
kubectl scale deployment myapp --replicas=5   # scale up on the fly

# Roll out a new version — K8s replaces Pods one at a time, watching readiness.
kubectl set image deployment/myapp server=myregistry/myapp:1.1.0
kubectl rollout status deployment/myapp        # watch the rollout progress
kubectl rollout undo deployment/myapp          # instant rollback if it goes wrong

What this shows: the Deployment's template is a Pod blueprint; replicas: 3 is the desired count. Kill a Pod (kubectl delete pod myapp-...) and the Deployment starts a replacement immediately — that's self-healing. The two probes matter a lot: the readinessProbe hitting your app's /healthcheck route tells Kubernetes when a new Pod is ready to receive traffic (so rollouts wait for it), and the livenessProbe restarts a hung container. resources.requests tells the scheduler how much to reserve; limits cap usage (blow past the memory limit and the container is OOM-killed and restarted). rollout undo is your safety net.

3. Services — a stable address for a moving set of Pods

Pods are ephemeral — they get new IPs every time they restart or reschedule. A Service gives the set a single, stable virtual IP and DNS name, and load-balances across whichever Pods currently match its label selector. Other Pods reach your app by the Service name, not by chasing Pod IPs. 

# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp              # routes to every Pod carrying this label
  ports:
    - port: 80              # the Service port other things call
      targetPort: 8080      # the containerPort to forward to
  type: ClusterIP           # internal-only virtual IP (the default)

kubectl apply -f service.yaml
kubectl get service myapp
# Inside the cluster, other Pods can now reach it at:
#   http://myapp        (same namespace)
#   http://myapp.default.svc.cluster.local   (fully-qualified)

What this shows: the Service's selector (app: myapp) is the same label the Deployment stamps on its Pods — that's the glue connecting them. Any Pod in the cluster can now call http://myapp and Kubernetes' internal DNS + load balancer routes it to a healthy replica, regardless of how many there are or what IPs they have. type: ClusterIP keeps it internal; to expose it to the outside world you use an Ingress (next).

4. Ingress — routing external traffic in (with HTTPS)

A ClusterIP Service is only reachable inside the cluster. An Ingress is the K8s equivalent of the Traefik setup earlier: it routes external HTTP(S) requests by hostname/path to internal Services, and (with cert-manager) provisions TLS certificates. An "ingress controller" (nginx-ingress, or Traefik running as the controller) actually implements the rules. 

# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt"   # auto-TLS via cert-manager
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.example.com]
      secretName: myapp-tls          # cert-manager fills this Secret in
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: myapp          # forward to the Service from step 3
                port:
                  number: 80

What this shows: external requests for app.example.com hit the ingress controller, which forwards them to the internal myapp Service on port 80, which load-balances to the Pods. The cert-manager annotation triggers automatic Let's Encrypt certificates stored in the myapp-tls Secret — same outcome as Traefik's ACME resolver, expressed the Kubernetes way. This is the full path: internet → Ingress → Service → Pod → your Go binary.

5. Config and secrets

Never bake config or credentials into your image. Kubernetes has two objects for this: ConfigMap for non-secret config and Secret for sensitive values. You mount them as environment variables (or files) into your Pods. 

# config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
data:
  PORT: "8080"
  CORS_ORIGIN: "https://app.example.com"
---
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secrets
type: Opaque
stringData:                # stringData is auto-base64-encoded for you
  JWT_KEY: "replace-with-a-real-secret"
  DATABASE_URL: "user:password@tcp(mysql:3306)/myapp?parseTime=true"

# In the Deployment's container spec, pull them all in as env vars:
          envFrom:
            - configMapRef: { name: myapp-config }
            - secretRef:    { name: myapp-secrets }

What this shows: config lives outside the image, so the same image runs unchanged in dev, staging, and prod — only the ConfigMap/Secret differ. envFrom injects every key as an environment variable your Go app reads with os.Getenv. Secrets are namespaced and access-controlled (in production, back them with a real secrets manager or sealed-secrets — plain Secrets are only base64-encoded, not encrypted at rest by default).

6. Putting it all together — the deploy workflow 

# 1. Build and push the image (your CI does this on every merge).
docker build -t myregistry/myapp:1.0.0 .
docker push myregistry/myapp:1.0.0

# 2. Apply all the manifests (a folder of YAML, or one combined file).
kubectl apply -f k8s/
#   configmap/myapp-config created
#   secret/myapp-secrets created
#   deployment.apps/myapp created
#   service/myapp created
#   ingress.networking.k8s.io/myapp created

# 3. Watch it come up.
kubectl get pods -w                 # -w = watch, live updates until 3/3 Running
kubectl rollout status deployment/myapp

# 4. Ship a new version — change the image tag and re-apply, or:
kubectl set image deployment/myapp server=myregistry/myapp:1.1.0
kubectl rollout status deployment/myapp    # zero-downtime, honors readinessProbe
kubectl rollout undo deployment/myapp      # rollback if needed

# Handy debugging commands every junior dev should know:
kubectl logs -f deployment/myapp           # stream logs from the Pods
kubectl describe pod <pod-name>            # events: image pull errors, OOM, etc.
kubectl exec -it <pod-name> -- sh          # shell into a running container
kubectl get events --sort-by=.lastTimestamp

Object cheat sheet

Object What it is Analogy
Pod One or more co-located containers (usually one) A single running instance
Deployment Keeps N identical Pods running; rolling updates A supervisor / autoscaler
Service Stable IP + DNS that load-balances to matching Pods An internal load balancer
Ingress Routes external HTTP(S) by host/path to Services The front door + reverse proxy
ConfigMap / Secret Config and credentials injected as env/files An .env file, but cluster-managed
Namespace A virtual cluster for isolating teams/envs A folder / tenant

Docker vs Kubernetes — when to reach for which

Docker builds and runs a container. Kubernetes orchestrates many containers across many machines. You always need Docker (or a compatible image builder) to produce the image; Kubernetes is the layer above that decides where images run, keeps them healthy, scales them, and networks them. For a hobby project or a single server, Docker Compose is plenty. When you need multiple machines, self-healing, zero-downtime rollouts, and horizontal scaling across a team, that's where Kubernetes earns its complexity. A good learning path is exactly this section's order: run the image with docker run, wire services with Compose, then graduate to Pods → Deployments → Services → Ingress on a local cluster like kind or minikube before touching a real cloud cluster.

Start local: install kind (kind create cluster) or minikube (minikube start), point kubectl at it, and apply the manifests above. Everything here runs on your laptop first — break things safely, then move to a managed cluster (EKS, GKE, AKS) once the workflow is muscle memory.
